# Operator runbook

## Startup and configuration

1. Generate `.env` once with `python scripts/configure.py`. The script refuses to overwrite an existing file and uses owner-only permissions on POSIX.
2. Back up the encryption key separately from the database. Losing it makes existing secret ciphertext unrecoverable.
3. Run the explicit schema migration before API/worker startup. Compose wires this dependency automatically.
4. Bootstrap a workspace using the CLI. Store its owner key in a password manager; it expires after 30 days by default.
5. Start API and worker with matching configuration. In Docker mode, pre-pull the configured catalog images.

| Variable | Default / purpose |
|---|---|
| `CLOUDER_ENCRYPTION_KEY` | Required Fernet key; generated by setup |
| `CLOUDER_DATABASE_URL` | `sqlite:///.data/clouder.db`; Compose overrides with PostgreSQL |
| `CLOUDER_DATA_DIR` | `.data`; persistent local object storage root |
| `CLOUDER_PROVIDER` | `simulated` or `docker` |
| `CLOUDER_DOCKER_SOCKET` | Runtime Unix socket path; default `/var/run/docker.sock` |
| `CLOUDER_DOCKER_API` | `v1.47`; daemon must support this API |
| `CLOUDER_COMPUTE_IMAGE` | `nginxinc/nginx-unprivileged:1.28-alpine` |
| `CLOUDER_DATABASE_IMAGE` | `postgres:17-alpine` (the supported UID/data-path contract) |
| `CLOUDER_LOADBALANCER_IMAGE` | `haproxy:3.0-alpine` |
| `CLOUDER_RESOURCE_QUOTA` | 20 non-deleted resources per tenant |
| `CLOUDER_STORAGE_QUOTA_BYTES` | 100 MiB logical object data per tenant |
| `CLOUDER_OBJECT_LIMIT_BYTES` | 10 MiB per object; browser upload also caps at 10 MiB |
| `CLOUDER_OPERATION_LEASE_SECONDS` | 180; minimum 120 |
| `CLOUDER_MAX_ATTEMPTS` | 4 |
| `CLOUDER_API_KEY_DAYS` | 30; maximum 365 |

If using the rootless socket override, Compose must mount the host socket at the path configured inside the worker. For example: host `CLOUDER_DOCKER_SOCKET=/run/user/1000/docker.sock`; override worker environment to `CLOUDER_DOCKER_SOCKET=/var/run/docker.sock`. Do not accidentally make the worker look for the host path inside its container.

## A resource stays pending

1. Read its operation in the console. Note operation ID, attempts, state, and sanitized error.
2. Check `docker compose logs worker` and `docker compose ps` (or the local worker terminal).
3. Check metadata connectivity and `GET /health/ready`.
4. In Docker mode, verify socket permissions, image availability, free disk/memory, and daemon API compatibility.
5. A crashed worker's running claim is eligible after its lease expires. Start a replacement worker and observe the operation; do not manually rewrite lease ownership.
6. Retry-budget exhaustion is terminal. Fix the provider issue, delete the failed resource to reconcile partial infrastructure, then recreate with a new name or after deletion succeeds. No generic retry endpoint is provided yet.

Creation retries use stable container names. Worker crashes after a runtime effect can cause repeat execution; this is expected. Do not remove ownership labels from managed containers. Ownership mismatches stop reconciliation instead of deleting unknown infrastructure.

## API is ready but a workload is down

`ready` is a last-provisioned control-plane state. Inspect the specific container on the dedicated runtime host; test the load-balancer endpoint or PostgreSQL health directly. There is no periodic drift scan yet. Do not use resource count as an uptime monitor.

## Backup and restore (manual preview procedure)

This is an operator procedure, not an implemented managed-backup product.

1. Schedule downtime and stop API/worker writes. Record code version, catalog images, and schema version.
2. Take a PostgreSQL metadata dump using `pg_dump` with credentials provided through a protected environment/secret file. For local SQLite, use SQLite's backup API after stopping processes; do not copy only the main file while WAL writers are active.
3. Snapshot/copy the object data volume. Preserve tenant UUID/hash layout and permissions.
4. Back up workload PostgreSQL separately using `pg_dump` or a documented physical-backup procedure; copying a live PostgreSQL data directory is not a consistent backup.
5. Protect and escrow the Fernet key separately. Do not include it in diagnostic archives or Git.
6. Restore into an isolated environment using the same schema/code version and key. Verify secret decryption, object checksums, resource ownership labels, and database contents before exposing ingress.
7. Record measured RPO/RTO from the drill. None has been established for this release.

The metadata database and Docker volumes are distinct state systems. Restoring only metadata does not restore deleted workloads. Restoring metadata to another Docker host requires explicit resource reconciliation/import design; do not blindly restart old jobs against unrelated containers.

## Storage pressure and orphan blobs

Logical deletion retains blobs. Monitor the physical volume independently. Stop API and worker, take a backup, build the set of referenced `(tenant_id, sha256)` pairs from `objects`, and remove only unreferenced hash-named files after an operator-reviewed dry run. No online garbage collector is included. Do not delete the entire data volume to resolve quota issues.

## Deploy and roll back

- Run quality, PostgreSQL, Docker integration, browser, and build gates before releasing.
- Take backups and record the schema version before changes.
- Deploy matching API and worker versions; allow active jobs to settle before changing provider configuration.
- For this initial schema, rollback means restoring the prior application image if schema compatibility is unchanged. Later migrations require their own explicit compatibility/rollback design.
- `docker compose down` preserves named volumes. **Do not use `down -v` unless intentionally destroying all control-plane and object data.** Tenant workload containers/volumes are managed separately from Compose.
- Never equate a successful image build with a successful restore drill or production readiness.

## Proposed alert thresholds (not achieved SLOs)

- Oldest unfinished operation age > 300 seconds: investigate worker/runtime backlog.
- Any terminal operation failure: review error and capacity/runtime state.
- Metadata readiness failure: remove API from ingress and investigate database health.
- Physical object volume > 80% full: plan cleanup/capacity before exhaustion.

Use an authenticated viewer key to scrape `/v1/metrics`; rotate before expiry. Configure actual alert routing externally. Future work includes workload metrics, worker heartbeat, distributed tracing, and measured latency/error budgets.
